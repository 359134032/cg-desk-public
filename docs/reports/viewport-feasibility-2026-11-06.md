# 地图视口扩展：验证与实验方案

日期：2026-11-06。

目标：保持地图格子、人物的像素尺寸，随绘制分辨率增加可见地图范围。FSR 可在绘制完成后放大输出，不负责提供画面外的地图内容。

## 已验证结果

用户通过游戏内“系统 → 窗口设定 → 窗口分辨率设定”切换为 800×600，并通过官方登录器重进地图。Computer Use 观察到内容区从约 640×480 增加到 800×600（外框分别为 642×507、802×627）；菜单明确显示“800 X 600”。格子、路灯等场景元素保持像素大小，画面容纳更多周围地图。这是游戏自身的视口扩展，不是 FSR 放大。

独立的 Config.exe 仅有画质、窗口模式、跳帧与声音选项，没有分辨率控件；此前仅检查该程序不足以判断游戏没有分辨率设置。实际分辨率开关位于游戏内，并提示下次启动生效。

1024×768 自定义实验组件已构建，并在用户明确同意后部署。用户通过官方登录器启动、进入地图，先确认“窗口显示正常”，随后明确反馈“已经测试了，达到了实际分辨率”。因此，启动进入游戏、正常窗口显示及实际分辨率达到 1024×768 已由用户实机确认。自动截图验收被用户物理 Esc 中断，未将用户反馈伪装为自动测量；边缘对象、点击落点、切地图、长时间运行仍未形成完整测试记录。

当前已撤回无改善效果的 V2.2，恢复用户实测通过的 V2.1 UI 修复版，原 EXE 与注册表未修改。当前实验代理 SHA-256 为 `353c3924a718132c3f2aabb59436929bb29414d9faece58912f7edac88e406c6`；Windows x86 DirectDraw 别名副本 SHA-256 为 `cc8687345e7ac20c2dcd21321634c191a035d145f442d0a403584fd77e72b1a1`。校验及回退记录保存在本地 `artifacts/viewport-research/installed-viewport-experiment.json`；`v21-user-validation.json` 记录启动与 UI 黑线修复验收。

本轮得到的是固定 1024×768 的实验结果，尚未加入随窗口自动调整的产品开关，也没有对账号安全作出保证。

## 已报告回归、启动修复与分项验收

用户随后报告 UI 背景图片出现规则横竖黑色拼接线，场景内其他角色的更新及部分资源刷新范围没有完整跟随视口扩大。附图位于角色选择界面，可见背景分块边界细缝。因此，先前的实机分辨率确认只代表尺寸生效，不能作为完整画面与动态对象验收通过。当前实验仍待修正，不应作为正式窗口台功能发布。

修复分别调查 UI 分块坐标/纹理采样、地图资源刷新边界与实体本地更新/剔除判断。服务器同步距离尚未证实，不将未知原因当作已定位问题。

最初 V2 同时加入以下两项修复，但用户实测启动出现内存访问错误，已撤下。V1 恢复后，用户确认能重新进入游戏：

- UI 黑线：背景 D3D 分块路径分别截断缩放后的位置与宽高，造成共享边界差 1 像素。只针对已核对的背景绘制调用修正右/下共享边界，不改变纹理坐标或场景人物大小。
- 资源覆盖：资源对象 flag `0x400` 路径仍按相对距离 ±16 格删除；V2 将四个有完整指令签名校验的内存立即数改为 20。临时写保护恢复与指令缓存刷新均有检查，不改磁盘 EXE、地图缓存尺寸或队列上限。
- 普通角色：用户补充异常主要发生在新增边缘。已检查的移动、动画调用链未发现同样的固定本地半径。资源修复不能等同于所有角色同步已经修复，也没有证据认定服务器 AOI 是原因。

进一步在独立 Windows DirectDraw7/Direct3D7 RGB 测试程序中复现：原系统对象的初始化、SetViewport、绘制与释放成功，V2 的直接 vptr 克隆替换在 SetViewport 访问异常退出（`0xc0000005`）。无需加载游戏或应用资源补丁即可复现，因此 UI 修复的接口实现已确认存在独立启动缺陷；没有把它归因为反外挂或服务器限制。

V2.1 将接口实现改为转发对象，保留系统对象原有 vptr。未改动的方法通过静态 x86 stdcall 转发桩，以系统原接口作为 this 参数调用；QI/IUnknown、CreateDevice、GetDirect3D 与 Release 保留接口身份和原引用行为。V2.1 暂停资源代码字节修改，用户通过官方登录器启动后明确反馈“能进入，黑线已消失”。该版本 DLL 哈希为 `353c3924a718132c3f2aabb59436929bb29414d9faece58912f7edac88e406c6`，已保留可恢复备份。

修订后的检查通过：723 项 UI 几何及接口行为检查、真实 Windows RGB 图形设备的初始化/身份/绘制/释放、22 项资源补丁/回退/保护恢复检查、21 个普通 DirectDraw 导出一致性检查。真实设备检查记录在 `real-d3d-facade-checks.json`，只执行独立程序中的系统图形 API，未加载游戏镜像；该独立主机的硬件设备路径不可用，不将其当作已测试。资源夹具只映射分析镜像，不执行游戏入口、导入或指令。

V2.2 曾保留 V2.1 的接口修复并单独启用资源半径 20 格。用户反馈“能进入，但边缘刷新仍无改善”，补充角色“靠近后才突然出现”，主要在新增边缘。只读探针对当前已校验进程核对，绘制尺寸确为 1024×768，四处内存立即数全部为 20，因此不能归为 DLL 或半径补丁未生效。报告位于 `runtime-68704-20261106-060446-f2b1fb50/runtime-report.json`；临时读取权限已恢复。此模式仅读取两个尺寸 DWORD 和四个指令字节，没有读取角色实体、账号、堆或网络数据。

对已保留证据的最后核对显示，角色消息处理 `0x5469e0` 在解析远端角色数据后进入 `0x475f10`，后者分配可用槽并直接调用 `0x4708d0` 创建角色；所检查分支未发现按旧分辨率范围筛掉角色的判断。远端删除消息另有按角色 ID 调用 `0x471900` 的路径。结合用户现象与实机半径试验无效，更倾向服务端角色下发/兴趣范围限制；这仍是推断，没有取得服务端配置或直接下发证据，不能称为已证实。

用户明确表示“如果是服务端原因就不改了”。据此停止刷新范围方向，不尝试修改服务端或网络协议。用户退出游戏后，已按所有权记录撤下 V2.2，重新安装哈希完全一致、已实测可启动且 UI 无黑线的 V2.1。资源半径试验关闭，源码默认同样关闭；1024×768 和 UI 修复保留。边缘角色出现距离未解决，不将整体动态对象验收标记为通过。

## 已解决的分析入口

普通分析进程没有启用管理员角色，基础进程查询及内存读取返回 Windows 错误 5。单独的管理员探针仍需标准 SeDebugPrivilege 才能读取目标。探针仅在自身 token 临时启用该权限，结束前已恢复，报告中启用、恢复均成功；没有关闭防护或修改系统持久设置。因此，早期的错误 5 不能作为反外挂阻止分析的证据。

探针核对进程路径、创建时间、主模块、原始文件 SHA-256，采集主模块 .text：地址 `[0x00401000, 0x005ad16c)`，1,753,452 字节，SHA-256：

`1e7f13e748c792586c7db2eb21d26d19f710bafecea02df6c2d6e44ad136d427`

运行时 PE 头不可用，采集范围明确采用已校验的磁盘 PE 段表，并由实际主模块范围约束；报告没有把磁盘头当作成功读取的运行时头。没有读取 .data、堆、账号、命令行或网络数据，也没有向游戏写入内存。离线派生文件仅用于分析，禁止执行或替换原游戏。

模块列表确认本次原生游戏使用系统 DDRAW.dll、D3DIM700.DLL；没有据文件名推断某个防护产品已运行。只读探针位于 `tools/CgDesk.ViewportProbe`，启动脚本为 `scripts/Start-ViewportProbe.ps1`。原始证据保存在本地被 Git 忽略的 `artifacts/viewport-research`，不随源码公开。

## 1024×768 实验设计

独立的 x86 DirectDraw 代理只在客户端初始化创建画布之前调整尺寸。它核对目标进程名、主模块基址、五处函数指令签名、四处资源指令上下文、调用位置、窗口模式、窗口所属线程、未初始化绘制上下文及当前 640/800 尺寸；任何条件不匹配都原样转发。

通过后显式写入六个尺寸字段：绘制宽高、窗口宽高、上下文 +0x94/+0x98。然后调用客户端原有 0x005080e0 更新镜头与界面派生字段，并按原窗口样式调整客户区。保留的 V2.1 不写游戏代码页；已撤回的 V2/V2.2 曾为资源试验改写四个内存立即数字节并恢复页面保护。不会修改账号、服务器或网络逻辑，也不移除缓存容量检查。部分应用失败时尝试恢复尺寸、派生字段和原窗口大小，并停止再次应用。

组件源码位于 `tools/CgDesk.ViewportExperimentNative`。部署脚本 `scripts/Set-ViewportExperiment.ps1` 默认只输出 Plan。实验使用两份新增 DLL：代理 ddraw.dll 与 Windows 自带 x86 DirectDraw 的别名副本 cgdesk_viewport_sys.dll。脚本绑定客户端 SHA-256、验证 x86 PE 和实验标记、拒绝覆盖任何同名文件；记录两文件的哈希，只允许移除仍与记录相符的自有文件。安装、回退均要求先正常关闭游戏；原 EXE 与注册表不改动。

该实验与窗口台的正式 FSR 链路分开验收。独立 host 已验证全部 21 个普通导出与系统别名逐一解析到相同地址，DirectDrawCreateEx 的系统和代理调用均返回 S_OK 及 COM 对象，非目标程序校验与状态查询边界检查通过。实际游戏启动、窗口显示和目标分辨率已由用户确认；边缘对象、点击落点、完整界面、切地图和长期运行尚未完成验收，不能据此直接作为通用产品功能发布。

恢复原生模式：正常退出游戏后，运行 `scripts/Set-ViewportExperiment.ps1 -GameExecutable <实际客户端路径> -Action Remove`，再通过官方登录器正常启动。脚本只移除安装记录中哈希仍匹配的两份实验 DLL，保留原 EXE 和用户已经选择的原生 800×600 设置。客户端更新后仍允许核对并移除自有 DLL，不要求新 EXE 继续匹配旧版本才可回退。

## 确切限制和风险

- 地图取图矩形在 0x004a0540 固定为玩家相对 X[-30,+21)、Y[-20,+31)，每轴最多 51 格；多层缓存固定 51×51×2 字节。直接增加枚举常量可能越界，实验不改这些常量。
- 按投影公式估算，1024×768 角落约需两条地图轴各偏移 16 格，理论上仍在缓存范围内；1920×1080 约需 26.25 格，会超过较短边界。此估算不包含高大建筑、动画、镜头移动，不能代替实测。
- 总绘制队列上限 4096，两类地物中间队列各 1024。大视口可能出现漏绘，不能简单删掉容量检查。
- 自定义代理可能产生崩溃、黑边、界面位置不完整或操作错位；静态分析和透明转发测试不能证明真实游戏兼容。
- 原生 800×600 使用游戏已有设置。自定义 1024×768 会加载额外代码并调整内部尺寸，账号与客户端防护风险无法保证为零；目前没有运营方对该具体改动的明确许可。
- 文件回退可恢复下一次正常启动的原生渲染，但不能撤销已经发生的服务器侧处置。

易玩通的[官方帐号保护说明](https://www.polchina.com.cn/def/defm.htm)并未明确允许这项具体扩展，不能据其一般性插件介绍推导自定义代理安全，也不应将其他地区或历史转载的处罚规则套用到本版本。
